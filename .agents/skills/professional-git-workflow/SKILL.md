# Professional Git Workflow

## Apply instruction precedence

Read the root and applicable nested `AGENTS.md` files, `CONTRIBUTING.md`, pull-request templates, issue templates, release instructions, and branch-protection guidance before changing Git or GitHub state. Follow repository-specific rules first when they are stricter. Stop and ask a maintainer when rules conflict or authority is unclear.

## Enforce metadata neutrality

Describe the work in all new Git and GitHub metadata. Never identify or credit the automation that performed it.

- Exclude AI agent, model, vendor, assistant, bot, and development-tool identities from branch namespaces, author or committer identities, co-author trailers, commit subjects and bodies, signed-off or provenance lines, tag names and annotations, and pull-request titles and bodies.
- Reject attribution patterns such as `ai/*`, `agent/*`, `bot/*`, `codex/*`, `chatgpt/*`, `gemini/*`, `claude/*`, `copilot/*`, `antigravity/*`, automated co-author trailers, tool signatures, and "generated by" credits.
- Preserve the existing human-configured Git identity. Do not edit `user.name` or `user.email`, invent a person, impersonate a maintainer, or add a synthetic co-author. If required identity is missing, stop before committing and ask the user to configure it.
- Mention a named product only when it is materially necessary to describe the software being changed. Never use that name as branch ownership, authorship, credit, or work provenance.
- Apply the policy to new metadata. Do not rewrite existing commits or rename a shared branch solely to clean up old attribution without explicit maintainer approval.

## Inspect before acting

1. Confirm the repository root and Git worktree.
2. Read the applicable instructions and inspect recent branch, commit, and pull-request conventions.
3. Inspect the current branch, default branch, status, remotes, and upstream relationship.
4. Identify pre-existing modified, staged, untracked, or conflicted files.
5. Determine whether the current branch belongs to the task and whether a pull request already exists.
6. Define the requested scope, acceptance criteria, likely validation, and correct base branch.

Use read-only inspection first. Useful commands include:

```text
git rev-parse --show-toplevel
git status --short --branch
git remote -v
git symbolic-ref --quiet --short refs/remotes/origin/HEAD
git log --oneline -n 12
git diff
git diff --cached
```

Do not assume the default branch is `main`. Do not stash, clean, reset, switch away from, or otherwise hide pre-existing work merely to obtain a clean tree. Treat unrelated changes as user-owned.

## Select or create the task branch

Reuse the current branch when it clearly belongs to the task. Create a branch only when changes are required and the current branch is the default branch or belongs to different work.

Before creating a branch:

1. Confirm the correct base and whether the working tree contains task changes.
2. Fetch the relevant remote when current network access and authorization permit it.
3. Bring a clean local base forward only with a fast-forward operation.
4. Branch from the current remote base when practical.
5. If unrelated changes or ambiguous ownership make switching unsafe, stop and ask instead of moving or stashing them.

Follow the repository naming convention. If none exists, use:

```text
<type>/<optional-issue-id>-<short-kebab-case-description>
```

Choose `type` from `feat`, `fix`, `hotfix`, `refactor`, `perf`, `docs`, `test`, `chore`, `build`, `ci`, or `security`. Use lowercase letters, digits, hyphens, and a single type separator. Keep the description specific and normally between two and six words.

Good branch names:

```text
feat/user-dashboard
fix/login-validation
docs/api-authentication
refactor/payment-retries
security/session-cookie-flags
feat/proj-123-user-dashboard
```

Reject branch names that contain a person or automation identity, use a tool or vendor as the namespace, expose a prompt or session identifier, or use vague words such as `work`, `changes`, `update`, or `task` without describing the behavior.

## Implement with a focused worktree

- Preserve all pre-existing and unrelated changes.
- Make only changes needed for the requested outcome.
- Follow repository style, architecture, generated-file policy, and dependency policy.
- Avoid drive-by cleanup and broad formatting churn.
- Add or update tests and documentation when behavior changes.
- Inspect status and diff throughout the work to catch scope drift early.

## Validate the change

Run the narrowest relevant checks first, followed by the repository's required suite when practical. Include applicable tests, linting, formatting checks, type checking, builds, security checks, schema validation, and manual verification.

Run `git diff --check` before committing. Review the complete diff for correctness, secrets, credentials, private data, debug code, generated noise, and accidental file changes.

Record the exact checks and outcomes for the pull request. Never imply that an unrun check passed. Explain skipped or failing checks and their impact.

## Build atomic commits

Follow the repository's established commit style. If none exists, use Conventional Commits:

```text
<type>(optional-scope): <imperative summary>
```

Use the same core types as branch naming. Add `revert` when reverting an earlier commit. Mark a breaking change using repository convention, commonly `!` and a `BREAKING CHANGE:` footer.

Before each commit:

1. Inspect `git status --short` and the working diff.
2. Stage only the intended paths or hunks.
3. Inspect `git diff --cached` in full.
4. Confirm the staged snapshot contains no secrets or unrelated changes.
5. Run or confirm the validation relevant to that snapshot.

Write commits that:

- Represent one coherent change and leave the repository in a usable state.
- Use a specific, imperative subject, normally no longer than 72 characters.
- Explain motivation and non-obvious tradeoffs in the body instead of narrating file edits.
- Reference issues using repository convention.
- Contain no automated-author attribution, synthetic co-author, tool signature, provenance footer, or prompt/session reference.

Avoid messages such as `updates`, `fix stuff`, `checkpoint`, `WIP`, `autosave`, or `address comments`. Describe the actual behavior changed.

Do not bypass commit hooks. Do not amend or rebase published commits without explicit authorization and awareness of collaborators.

## Push safely

Push only the task branch and set its upstream when needed:

```text
git push -u origin <branch>
```

Never push directly to a protected or default branch unless the repository explicitly requires it and the maintainer authorizes it. Never force-push without explicit authorization. When authorized to update rewritten history, use the repository-approved safe method, normally `--force-with-lease`, and verify the remote branch first.

Do not expose credentials in command arguments, logs, commits, or pull-request content.

## Create or update the pull request

Check for an existing pull request for the branch and update it instead of creating a duplicate. Use the repository's preferred GitHub interface.

Set the base to the confirmed target branch. Use the repository title convention; when none exists, use the same work-focused format as the primary commit.

Complete `.github/pull_request_template.md` accurately:

- Summarize the outcome and why it is needed.
- List the meaningful changes without restating every diff line.
- List exact validation commands or checks and their results.
- Describe risk, rollout, rollback, migrations, compatibility, security, and operations when relevant.
- Link the issue with the repository's closing syntax only when the pull request fully resolves it.
- Add visual evidence for user-interface changes when practical.
- Disclose unfinished work, known limitations, and follow-ups.

Keep the pull request as a draft while it is intentionally incomplete, unvalidated, or awaiting a prerequisite. Do not claim readiness when required checks fail.

Exclude automated-author credit, tool identities, generated-by notices, synthetic co-authors, and prompt/session provenance from the title and body.

## Follow CI and review

1. Monitor required checks and inspect failure details.
2. Fix failures caused by the branch; distinguish unrelated infrastructure failures accurately.
3. Address review feedback with focused changes and meaningful commits.
4. Explain respectfully when feedback should not be applied, using repository evidence.
5. Resolve review threads only after the concern is addressed or the reviewer agrees.
6. Update the pull-request description when scope, validation, risks, or rollout changes.

Do not approve the agent's own work, dismiss reviews, bypass required checks, close the pull request, or merge without explicit authorization.

## Handoff clearly

Report:

- The active branch and base branch.
- The commits created or updated.
- The validation performed and exact results.
- The pull-request URL and draft/ready status, or why no pull request was opened.
- CI and review status when checked.
- Remaining risks, failures, decisions, or blockers.

Keep the handoff factual. Never claim an action, check, approval, or merge that did not occur.
